# 뉴스·커뮤니티 사이트 지원 계획 (2026-11-26, 계획만)

> 이 문서는 계획입니다. 코드는 바꾸지 않았습니다. **어느 사이트를 넣을지, 어떤 권한을 더할지는 Spruce가 정합니다.**

## 결론 먼저

1. **첫 사이트는 네이버 뉴스 하나**를 추천합니다.
   - 기사 페이지가 스스로 부르는 댓글 JSON(`apis.naver.com/commentBox/cbox/web_naver_list_json.json`)이 있어, YouTube에서 쓰는 방식(페이지가 받는 응답을 같은 모양으로 받아 파싱)을 그대로 옮길 수 있습니다.
   - 시각이 **초 단위**(`regTime`)라 YouTube에서 '며칠 전' 때문에 보류되던 시간 몰림·함께 쓴 작성자 신호가 제대로 돕니다.
   - 공감·비공감, 답글(1단계), 가린 아이디(`maskedUserId`), 작성자 번호(`userIdNo`)가 다 있어 지금 신호를 거의 그대로 씁니다.
   - 포털이라 한 커뮤니티의 이용자층에 묶이지 않습니다. 분야(정치·경제·사회·연예·스포츠…)를 골고루 담은 검증 세트를 만들 수 있습니다.
   - 댓글 조작 논란과 참고 연구(`docs/signals.md` 3장, 네이버 뉴스 댓글 1억 건)가 모두 이 사이트라 근거를 견주기 좋습니다.
2. **커뮤니티는 한 곳만 먼저 넣지 않고, 이용자층이 다르다고 흔히 알려진 두 곳을 같은 단계에 함께** 넣습니다(사이트 고르기 자체가 쏠림이 되지 않게). 기술로는 **디시인사이드**(댓글 JSON, 초 단위 시각)와 **루리웹**(서버가 그린 HTML, 분 단위 시각, robots 허용)이 가장 쉽습니다. 짝은 Spruce가 정합니다.
3. 권한은 **선택적 권한(`optional_host_permissions`)** 으로 사이트마다 사용자가 켜게 하는 방식을 추천합니다. 설치 때 모든 사이트 권한을 받지 않고, 업데이트할 때 확장이 꺼지는 일(권한이 늘면 브라우저가 확장을 멈추고 다시 승인받음)도 피합니다.
4. 원칙은 그대로입니다: **저장하지 않음**(메모리에만), **원격 코드 없음**(사이트 코드를 불러 쓰지 않음, 라이브러리는 `vendor/`), 의심 점수는 **행동·구조만**, '조작' 판정 문구 금지, 작성자 이름 기본 가림.

## 1. 대상 사이트 후보

### 확인 방법 (2026-11-26)
- robots.txt: 사이트마다 1번 요청.
- 페이지: **headless Edge**(창 없음, 음소거, 로그인 없음, 새 임시 프로필)로 사이트마다 글 1~2개만 열어, 댓글이 어떤 요청으로 오는지(네트워크)와 DOM 모양을 봤습니다. 대량 수집은 하지 않았고, 받은 원문은 저장소에 넣지 않았습니다(`qa/`는 gitignore).
- 로그인이 필요한 곳은 로그인하지 않았습니다. 확인 못 한 것은 그렇게 적었습니다.

**요청 예절 (모든 사이트 공통으로 제안)**
- 사용자가 연 그 글에서, 사용자가 '분석'을 누를 때만 수집합니다. 다른 글·작성자 이력·목록을 따라가지 않습니다.
- 페이지가 '댓글 더보기'로 부르는 **같은 요청**만 씁니다(같은 쿠키·Referer가 붙음). 숨은 API를 새로 찾아 쓰지 않습니다.
- 동시 1개, 요청 사이 최소 0.5초(YouTube는 동시 3개·100ms지만 뉴스·커뮤니티는 더 보수적으로). 429·5xx는 지금 `WV.withBackoff`처럼 물러나고, 이어서 막히면 멈추고 안내합니다.
- 한 번에 최대 1,000개(YouTube와 같은 상한, 사용자가 3,000까지 고를 수 있음). 그보다 많으면 '고르게 무작위'로 뽑고 수집 비율을 밝힙니다(객관성 기준 7).

### 사이트별 메모
**네이버 뉴스** (기사 1개에서 확인)
- 설정 응답(`web_naver_config_info_json.json`)에 `useReply`, `useVote`, `displayMaskedUserId`, `useStats`(성별·연령 통계) 같은 항목이 있습니다.
- 목록 응답 항목: `commentNo`, `parentCommentNo`, `replyLevel`, `replyCount`, `contents`, `userIdNo`, `maskedUserId`, `userName`, `regTime`, `modTime`, `sympathyCount`, `antipathyCount`, `best`, `deleted`, `blind`, `hiddenByCleanbot`, `shareCommentLink`, `exposedUserIp` 등.
- 페이지는 `pageSize=5`로 부르고, 정렬은 공감순·최신순 등(설정의 `sortTypes`). 한 번에 몇 개까지 되는지는 **확인 안 함**.
- 클린봇이 가린 댓글·삭제 댓글·블라인드가 있어 **수집 범위 안내에 '가려진 댓글 N개'** 를 함께 적어야 합니다.
- **쓰지 않을 것**: 성별·연령 통계(`useStats`), 작성자 댓글 이력(사이트에서 공개되지만 따라가지 않음), `exposedUserIp`.
- 연예(`m.entertain.naver.com`)·스포츠(`m.sports.naver.com`)는 다른 페이지라 다음 단계에서 따로 확인합니다.
- 네이버 자체 제한(하루 댓글 수 제한 등)이 있어 '다작'의 자연 기준선이 YouTube와 다를 수 있습니다 → 검증 세트로 확인.

**디시인사이드** (HIT 갤러리 글 1개에서 확인)
- 댓글은 `POST https://gall.dcinside.com/board/comment/` JSON: `no`, `parent`, `user_id`, `name`, `ip`, `reg_date`(초), `depth`, `del_yn`, `nicktype`. 댓글 추천 수는 없습니다(글 추천만).
- 유동(비회원)은 `user_id`가 비고 이름(흔히 'ㅇㅇ')과 IP 앞 두 자리로만 구별됩니다. 같은 'ㅇㅇ'라도 다른 사람이고, 같은 IP 앞자리도 여러 사람일 수 있습니다 → **작성자 신호는 고닉만 '계정', 유동은 '부분 구분'으로 낮춰** 다룹니다(3장).
- robots가 특정 갤러리(주식·야구 등)의 글·댓글 보기를 막습니다 → 그 갤러리에서는 쓰지 않음(안내).
- 댓글이 여러 쪽이면 요청에 쪽 번호가 들어갑니다(요청 본문은 **확인 안 함**).

**루리웹·클리앙·에펨코리아·네이트판**
- 댓글이 HTML에 이미 그려져 있습니다. 한 쪽에 다 있으면 요청이 필요 없고, 여러 쪽이면 다음 쪽 HTML을 받아 같은 파서로 읽습니다(쪽 나누기 방식 **확인 안 함**).
- 루리웹은 'BEST' 댓글이 위에 한 번 더 나옵니다 → id로 중복을 없앱니다.
- 에펨코리아·네이트판은 robots가 글 페이지를 막습니다. 사용자가 연 페이지를 읽는 것과 크롤러는 다르지만, **사이트의 뜻을 존중해 뒤로 미루기를 추천**합니다.

**다음 뉴스·더쿠·Reddit**: 이번에 확인하지 못했습니다. 다음 뉴스는 댓글 기능이 기사마다 꺼져 있거나 눌러야 열리는지 실제 창에서 다시 봐야 합니다. 더쿠·Reddit은 사람 확인 페이지가 떠서, 사용자가 실제로 쓰는 브라우저(로그인 없이)에서 다시 봐야 합니다.

## 2. 객관성

### 사이트 고르기
- 사이트를 넣는 것 자체가 쏠림이 될 수 있습니다. 한 이용자층의 사이트만 지원하면 '그 쪽 댓글만 의심받는 도구'가 됩니다.
- 원칙: **커뮤니티는 이용자층이 다르다고 흔히 알려진 곳을 짝으로 같은 판(버전)에 함께** 넣습니다. 한쪽만 먼저 내보내지 않습니다.
- 사이트의 성향을 문서·화면에 적지 않습니다(그것도 판단입니다). 짝을 고른 이유는 '이용자층이 겹치지 않게'로만 적습니다.
- 포털(네이버 뉴스)은 분야별로 검증 세트를 고르게 만듭니다.

### 자연 반복 기준이 사이트마다 다름
- 커뮤니티에는 밈·유행어·말투('ㄹㅇ', '개추', 'ㅋㅋ' 줄, 정해진 반응 문구)가 많습니다. 서로 다른 사람이 같은 말을 쓰는 것이 자연스럽습니다.
- 지금 거르기(짧은 반응, 흔한 인사·응원, 본문 인용, 사슬 묶음)를 그대로 쓰고, **사이트별로 추가 거르기**를 둡니다:
  - 글 제목·본문 인용(지금 '영상 제목·설명 인용'과 같은 규칙, 문서 본문으로).
  - 짧은 반응 낱말 목록을 사이트별 사전으로 확장(낱말은 일반 반응만, 대상·인물 이름 없음).
  - YouTube 전용 규칙(타임스탬프, 참여 요청 영상)은 다른 사이트에서 끕니다.
- 사이트별 기준은 **그 사이트의 검증 세트로만** 정합니다. 한 글에 맞추지 않습니다.

### 점수는 행동·구조만
- 의심 점수 항목은 지금처럼 문구 겹침, 서로 다른 작성자 수, 같은 작성자 반복, 시간 몰림, 긴 문장 겹침뿐입니다(`lib/weights.js`).
- 비공감·반대 수는 '반응'으로 보여 주기만 하고 점수에 넣지 않습니다(누가 비공감을 많이 받는지는 내용에 대한 반응이라 행동·구조 신호가 아님).
- 바꿔 넣기 테스트(`tests/run.mjs`)를 사이트별 입력 모양(익명 작성자, 초 단위 시각)으로도 돌립니다.
- '조작' 판정 문구 금지, '의심 신호 점수 + 근거'만.

### 근거가 부족하면 보류
- 작성자 구분이 약한 사이트(네이트판의 'ㅇㅇ', 디시 유동, 더쿠 익명)는 **작성자 신호를 보류**하고 그 이유를 보여 줍니다.
- 상대 시각만 있는 사이트(에펨코리아 '4 시간 전')는 시간 신호를 보류합니다(지금 '며칠 전' 처리와 같음).

### 검증 세트와 치우침 점검
- 사이트마다 `fixtures/validation-set.json` 모양의 목록을 따로 둡니다(원문은 로컬 `fixtures/set/`만).
- 네이버 뉴스: 분야 6개(정치·경제·사회·국제·생활문화·IT과학) × 기사 5개, 언론사 다양하게, 정치 기사는 여러 언론사·여러 쟁점으로.
- 커뮤니티 짝: 같은 시기·같은 화제의 글을 두 사이트에서 같은 수로(예: 같은 뉴스에 대한 글 각 5개) + 화제와 무관한 일상·게임 글.
- 통과 기준(지금 객관성 기준 9를 그대로): 오락·일상 글 의심 비율 ≤ 5%, **짝 사이트 사이 차이 ≤ 5%p**, 정치 기사 쟁점별 차이 ≤ 5%p. 넘으면 원인을 규칙의 결함에서 찾고(사슬 묶음 때처럼), 특정 글에 맞춰 가중치를 바꾸지 않습니다.

## 3. 구조 설계

### 지금 YouTube에 묶여 있는 곳
| 곳 | 묶인 것 |
|---|---|
| `sidepanel/sidepanel.js` | `videoIdOf(tab)`(주소에서 `v=`), 오류 문구 '영상', `send()`가 넣는 파일(`content/youtube.js`), `commentUrl()`(YouTube 주소), `gotoComment()`의 `ytNavigateToComment`·page-bridge, `checkVideo()` |
| `content/youtube.js` | 수집·파싱·댓글 열기 전부(메시지 `WV_EXTRACT`, `WV_COLLECT_ALL`, `WV_FOCUS*`) |
| `content/parse.js` | 일반 도구(`parseCount`, `parseRelativeTime`, `seededShuffle`, `withBackoff`, `sampleRandom`)와 YouTube 전용(`parseInnertubeComments`, `findCommentToken`, `parseWatchHtml`)이 섞여 있음 |
| `lib/patterns.js` | 영상 간 교차가 `doc.meta.videoId`를 씀 |
| `lib/signals.js` | 자연 반복 중 타임스탬프·참여 요청 영상은 YouTube 전용 |
| `lib/*` 문구 | '이 영상', '영상 전체' |
| `manifest.json` | YouTube만 |

### 나누는 방법
1. **`lib/sites.js` (새로, 순수 함수, 테스트 가능)**: 사이트 목록 한 곳.
   ```js
   // 패널이 쓰는 사이트 정보. 주소만 보고 판단한다(페이지에 들어가지 않음).
   SITES = [{
     site: "youtube" | "naver-news" | ...,
     match(url) -> docKey | null,       // 영상 id, "001,0016463573" 같은 기사 키, 글 번호
     origins: ["https://n.news.naver.com/*"],  // 권한 요청에 쓰는 주소
     files: ["content/common.js", "content/naver-news.js"], // 필요할 때 넣는 스크립트
     word: { doc: "기사", docs: "기사들" },  // 화면 문구: 영상/기사/글
     capabilities: { time: "second", authorKey: "account", dislikes: true, replies: 1 },
   }]
   ```
2. **`content/common.js`**: `parse.js`의 일반 도구를 옮기고, 사이트 어댑터를 받는 메시지 처리기 하나를 둡니다. 메시지 이름(`WV_COLLECT_ALL`, `WV_FOCUS` 등)은 그대로라 패널은 사이트를 몰라도 됩니다.
   ```js
   // 어댑터가 채우는 모양. content/<site>.js 가 WV.registerAdapter(adapter)로 등록한다.
   adapter = {
     site,
     docMeta() -> Doc,                                 // 제목·작성자·본문(인용 거르기에 씀)
     collect({ max, order, includeReplies, onProgress, isCancelled }) -> { doc, comments, coverage },
     focus(comment) -> { ok, via, reason },            // 페이지에서 이 댓글 보기
     permalink(doc, comment) -> string | null,         // 새 탭으로 열기
   }
   ```
   YouTube 전용 파싱은 `content/youtube-parse.js`로 옮기고, page-bridge가 쓰는 메인 월드 전역(`__wvParse`)은 지금 판(v3)을 지킵니다.
3. **사이트별 파서는 순수 함수**(응답 JSON 또는 HTML 문자열 → `Comment[]`)로 두고, 실제 응답 **모양**을 본뜬 합성 fixtures로 `tests/run.mjs`에서 시험합니다(원문 없음).
4. **패널**: `videoIdOf` → `docKeyOf(tab)`(sites.js), `S.doc.meta.videoId` → `S.doc.meta.docKey`, '영상' 문구 → `word.doc`. 오류 문구는 "지원하는 페이지에서 사용하세요(YouTube 영상, 네이버 뉴스 기사…)".
5. **`lib/`는 사이트를 모르게**: 사이트 차이는 `doc.meta.capabilities`와 `ctx`로만 받습니다.
   - `capabilities.time`이 `relative`면 시간 신호 보류(지금 '며칠 전'과 같은 길).
   - `capabilities.authorKey`가 `none`/`partial`이면 작성자 신호 보류 또는 '부분 구분' 표시.
   - 자연 반복 규칙은 `ctx.site`로 켜고 끔(타임스탬프는 YouTube만).
   - 영상 간 교차 → '문서 간 교차'(`docKey` 기준, 같은 사이트 안에서만. 사이트 사이 작성자 맞추기는 하지 않음 — 다른 사이트의 같은 닉네임은 다른 사람일 수 있음).

### 공통 데이터 모양 (지금 스키마 유지, meta만 넓힘)
```
Doc { id, site, url, title, author, publishedAt, text, meta: { docKey, capabilities, collection: { method, order, total, collected, hidden } }, extractedAt }
Comment { id, docId, parentId, author, authorId, text, likes, createdAtRaw, createdAtApprox, edited, meta: { dislikes?, best?, authorKeyKind } }
```
- `authorId`: 네이버 `userIdNo`, 디시 고닉 `user_id`(유동은 `name+ip`를 해시한 키, `authorKeyKind: "partial"`), 루리웹 회원 번호, 클리앙 `data-author-id`, 에펨 `member_` 번호. **모두 메모리에서만, 화면에는 '작성자 N'** (지금처럼 가림).
- `collection.hidden`: 삭제·클린봇·블라인드 수 → 수집 범위 안내에 함께.

### '페이지에서 이 댓글 보기'
순서(지금 YouTube와 같은 생각): ① 화면(DOM)에 있으면 스크롤 + 강조 → ② 사이트가 쓰는 방법으로 그 댓글을 불러오기 → ③ 새 탭으로 영구 링크 → ④ 못 하면 안내.
| 사이트 | ② | ③ 영구 링크 |
|---|---|---|
| 네이버 뉴스 | 댓글 목록을 '더보기'로 그 댓글이 나올 때까지(정렬을 최신순으로 바꿔 시각으로 위치 짐작) — 실측 필요 | `shareCommentLink`(응답에 있음, 확인 안 함) |
| 디시 | 댓글 쪽 이동(페이지의 쪽 단추 누르기) | 확인 안 함 |
| 루리웹 | 댓글 쪽 이동 | `#ct_<id>`가 되는지 확인 필요 |
| 클리앙 | 한 쪽에 다 있으면 ①로 끝 | 주소 `#<comment_sn>` (앵커 `span.comment_point#<sn>` 있음) |
| 에펨코리아 | 페이지 함수 `findComment(id)` | `/<글>/<댓글>#comment_<댓글>` (DOM에 있음) |
- 같은 탭에서 주소를 바꾸면 새로고침이 됩니다. 사용자가 글을 쓰던 중일 수 있으니 같은 탭 이동은 하지 않고 ③은 **새 탭**으로만.
- 페이지 함수를 부르려면 메인 월드에 넣어야 합니다. 사이트 코드를 불러오지 않고, 우리 파일만(`world: "MAIN"`) 넣습니다(원격 코드 없음).

**권한을 더하는 것은 Spruce가 정합니다.** 아래는 필요한 목록과 추천 방식입니다.

### 사이트별 필요한 주소

### 방식 견주기
| 방식 | 장점 | 단점 |
|---|---|---|
| `host_permissions`에 넣기 | 지금 구조 그대로(정적 content script) | 설치 때 모든 사이트 권한을 요구. 업데이트로 권한이 늘면 브라우저가 확장을 멈추고 다시 승인받음 |
| **`optional_host_permissions` (추천)** | 사용자가 쓰는 사이트만 켬(최소 권한). 업데이트해도 멈추지 않음 | 패널에 '이 사이트에서 쓰기 켜기' 단추 필요(`chrome.permissions.request`는 사용자가 누를 때만 됨). content script는 정적 등록 대신 `chrome.scripting.executeScript`로 필요할 때 넣기(지금 `send()`가 이미 이렇게 다시 넣음) |
| `activeTab`만 | 권한 경고 없음 | 아이콘을 누른 순간·그 탭에만 잠깐. 사이드 패널을 연 뒤 페이지를 옮기면 사라짐. 사이드 패널 열기와 함께 주어지는지 **확인 안 함** |

- YouTube는 지금처럼 기본 권한으로 둡니다(이미 받은 권한).
- 지금 API 권한은 `sidePanel`, `scripting`, `offscreen`입니다(v0.12.1에서 `activeTab`은 뺐음: YouTube 호스트 권한으로 충분). 이 밖의 새 API 권한(`activeTab`, `storage`, `cookies`, `webRequest` 등)은 **더하지 않습니다**. 위 표의 `activeTab` 방식을 고르면 그때 다시 넣어야 합니다. 켠 사이트 목록은 브라우저가 권한으로 기억하므로 따로 저장할 필요가 없습니다.
- COEP/COOP(확장 페이지 설정)는 content script와 상관없어 그대로 둡니다.

| 1-1. 네이버 댓글 열기 ② | '더보기'로 찾아 강조 | 중 | 실측 (성공률·시간) |

## 6. 위험

| 위험 | 무엇이 일어나나 | 줄이는 법 |
|---|---|---|
| 사이트 구조 변경 | 수집이 0개거나 틀림 | 사이트 코드는 어댑터 한 파일에, 선택자·키 이름은 맨 위 한 곳에. 0개·이상한 값이면 '이 사이트 모양이 바뀐 것 같아요' 안내(조용히 빈 결과 금지). 응답 모양 fixtures 테스트 |
| 약관·robots | 사이트의 뜻에 어긋남, 항의 | 사용자가 연 글·사용자가 누를 때만, 페이지와 같은 요청, 사람 속도, 상한. robots가 막은 곳은 뒤로. 사이트별 결정은 Spruce |
| 차단 (429, 확인 페이지, IP 차단) | 사용자 계정·IP가 그 사이트에서 막힘 | 동시 1개, 0.5초 이상 간격, 물러나기, 이어서 막히면 멈춤. 확인 페이지가 뜨면 우회하지 않고 안내 |
| 개인정보 | 작성자 노출, 신상 추정 | 작성자 기본 가림, IP 앞자리·성별 연령 통계·작성자 이력은 쓰지 않거나 메모리 안 구분 키로만. 출신·성향·지역 추정 금지 |
| 저장 | 원칙 위반 | 지금처럼 메모리에만. 권한 켜기 상태 외에 아무것도 저장하지 않음 |
| 사이트 고르기 쏠림 | 한쪽만 의심받는 도구로 보임 | 커뮤니티는 짝으로, 짝 치우침 점검 통과 전에는 내보내지 않음 |
| 사이트별 자연 반복을 놓침 | 밈·유행어가 의심 묶음으로 | 사이트 검증 세트로 거르기 규칙 확인(사슬 묶음 거르기는 이미 있음) |
| 작성자 구분이 약한 사이트 | 'ㅇㅇ'를 한 사람으로 오인 | `authorKeyKind`로 작성자 신호 보류 |

## 확인 못 한 것
- 다음 뉴스 댓글(기사 2개에서 댓글 영역 숨김, 요청 없음), 더쿠·Reddit(사람 확인 페이지), 언론사 자체 댓글.
- 네이버 댓글 JSON을 확장(content script)에서 불러도 CORS가 통과하는지, 한 번에 받을 수 있는 수, `shareCommentLink`로 그 댓글이 열리는지.
- 디시 댓글 요청 본문(쪽 번호·페이지 값), 루리웹·클리앙·에펨·네이트판의 댓글 쪽 나누기와 답글 깊이, 클리앙의 시각·공감 수 표시.
- 각 사이트 약관 조항을 하나씩 읽지는 않았습니다(robots만 확인).
- `activeTab`이 사이드 패널 열기와 함께 주어지는지.
- '하루 변경 빈도'는 잰 값이 아니라 추정입니다(네이버·디시는 오늘 날짜의 스크립트 판 번호가 붙어 있어 프런트 배포가 잦아 보이지만, 응답 모양은 오래 그대로로 알려짐).
